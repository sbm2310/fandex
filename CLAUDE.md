# Fandex

A collection app for fans who collect across formats — comics, manga, fantasy books, premium figures (Hot Toys and similar), and LEGO — organized **by universe and character** rather than by product type, with AI that makes adding items nearly effortless.

## Why this exists

Existing collector apps are either single-category (LEGO-only like Brickset/Rebrickable apps, figure-only like iCollect or Toy Collector) or generic catalogers with blank fields (Koillection). AI photo scanners (Toyzie, SnapToy) already identify one item at a time and give a value, so "scan one item and value it" is not our differentiator.

Nobody connects a collection the way fans think about it: "everything I own from Middle-earth / Batman / One Piece" across books, figures and LEGO.

## Core features (differentiators)

1. **Universe layer** — franchise and character pages that link items across categories, with "you're missing…" suggestions.
2. **Shelf-photo import** — photograph a whole shelf; AI identifies every item and adds them in one go.
3. **Ask your collection** — natural-language questions ("What Batman stuff do I own?", "Which manga series am I missing volumes of?", "What's arriving this month?").
4. **Pre-orders & releases** — track pre-orders (Hot Toys can sit for a year+), payment reminders, release-date slips, LEGO retirements; event-driven notifications.

## Decisions made

- **Name:** Fandex
- **Market:** real users, English, launching for the US
- **Platforms:** iPhone first, then Android and web (same codebase)
- **Stack:** TypeScript end to end
  - Client: React Native + Expo (iOS, Android, web from one codebase)
  - Backend: Node.js with TypeScript — NestJS + Prisma (decided in Stage 2 planning)
  - Database: PostgreSQL
- **Dev machine:** Intel MacBook Pro — use Expo cloud builds (EAS) for iOS builds; test on a real iPhone via Expo Go / dev builds
- **Approach:** long-term project, delivered in stages; every stage ends with a working, demo-able version

## Catalog data sources

| Category                   | Source                                           | Notes                                                                                                                          |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Books / fantasy            | Open Library                                     | ISBN barcode scanning. Google Books rejected (see below)                                                                       |
| Comics                     | Open Library (trade paperbacks / graphic novels) | Comic Vine is **non-commercial only** (key revoked otherwise) — not used. Single issues later, e.g. Metron (terms unverified). |
| Manga                      | Open Library (volumes by ISBN)                   | AniList: free only under $150/mo revenue and bans use in "competing list/tracker" apps — not used without written permission.  |
| LEGO                       | Rebrickable                                      | In use (Task 9). Terms checked 2026-10-05 (see below). Brickset kept as fallback.                                              |
| Hot Toys / premium figures | **No known public API**                          | Biggest risk. Build our own catalog: AI extraction from photos + community contributions. Potential moat.                      |

Verify current terms, rate limits and attribution requirements for each API before integrating.

**Open Library (verified 2026-10-04):** 1 req/s by default, 3 req/s with an identifying `User-Agent` (`Fandex/0.1 (https://github.com/sbm2310/fandex)`; native only, browsers can't set it). Cache responses; requests only on behalf of a person, no bulk crawling. Cover URLs by ISBN are limited to 100/IP/5 min — always build covers from cover IDs (`/b/id/{id}-M.jpg`), which are unlimited. No formal attribution requirement; we credit Open Library in the app and README anyway. Coverage check (2026-10-04): 10/10 sample ISBNs found with covers, incl. 2025 releases, manga and comics.

**Rebrickable (terms checked 2026-10-05; archive copy read, confirmed on the live site by the owner):** "The Rebrickable API may be used for any purpose, including commercial." Crediting Rebrickable is appreciated (not required); set images may be shown/hotlinked. **Not allowed:** automated scraping/downloading outside the API, and **using Rebrickable content to train AI models** (a Stage 4 constraint). Requires a free API key: `REBRICKABLE_API_KEY` in `apps/api/.env` (optional; without it LEGO search answers 503 and cached sets are still served). Throttled to ~1 req/s (we space calls 1 s apart). The site is behind a Cloudflare bot check, so its pages can't be read by tools — never try to bypass it.

**Google Books — rejected (2026-10-04):** the Google APIs Terms forbid creating "permanent copies" of content or caching beyond cache headers (saving to a collection or our DB is a permanent copy); the Books terms forbid charging users without a separate agreement; display requires a "Powered by Google" logo and a link per result. Revisit only with a Google agreement.

## Stage 1 decisions (settled 2026-10-04)

- **Scope:** books only, from Open Library (keyless and CORS-friendly, so the app calls it directly). ISBN misses show a not-found message suggesting a title search; manual entry may come later. Manga, comics and LEGO wait for the Stage 2 backend (Comic Vine/Rebrickable keys can't live in the client; Comic Vine has no CORS).
- **Repo:** npm-workspaces monorepo — `apps/mobile` (Expo), `packages/core` (pure TS: domain types, ISBN utils, catalog adapters; consumed as TS source via `main: src/index.ts`). Stage 2 adds `apps/api`.
- **Client:** latest stable Expo SDK (57 at time of writing), TypeScript strict, Expo Router, `StyleSheet` + a small theme file (light/dark), TanStack Query for both catalog search and the collection.
- **Persistence:** local only, behind a `CollectionRepository` interface; Stage 1 implementation uses AsyncStorage. Stage 2 swaps in an API-backed repository.
- **Domain model:** catalog entries (`CatalogBook`) are separate from owned copies (`CollectionItem`, which snapshots the catalog entry).
- **ISBN scanning:** `expo-camera` on iOS/Android; manual ISBN entry everywhere (scan hidden on web).
- **Testing on device:** Expo Go on a real iPhone (no Xcode installed → no simulator). No Apple Developer account needed for Stage 1.
- **Tooling:** TypeScript pinned to **6.0.x** (matches Expo SDK 57; ts-jest and typescript-eslint don't support TS 7 yet). Jest (ts-jest in `core`, `jest-expo` in the app), ESLint flat config + Prettier, GitHub Actions CI (format, typecheck, lint, test). Each workspace owns its `typecheck`/`lint`/`test` scripts; the root runs them across workspaces.
- **Git:** public GitHub repo, one commit per task.

### Monorepo / tooling gotchas (learned in Task 1)

- **Single React version:** root `package.json` has `overrides` pinning `react`/`react-dom` to the app's versions. Without it npm hoists a newer React (peer `"*"`) to the root → duplicate React at runtime. Update the overrides whenever the Expo SDK bumps React. Check with `npm ls react`.
- **Add app dependencies with `npx expo install <pkg>`** (from `apps/mobile`) to get SDK-compatible versions; for dev deps, move them into `devDependencies` afterwards (its `-- --save-dev` passthrough is unreliable).
- **ESLint 9, not 10:** `eslint-config-expo` → `eslint-plugin-react` doesn't support ESLint 10 yet. `eslint-import-resolver-typescript` is a direct app devDependency so `eslint-plugin-import` can find it (npm nests it otherwise).
- **App test timeout is 15 s** (`jest.testTimeout` in `apps/mobile/package.json`): GitHub's 2-core runners are much slower than a dev Mac, and the first screen test in a file timed out at Jest's 5 s default (Task 4).
- **Test runners:** `core` uses Jest 30 (ts-jest); the app uses Jest 29 (`jest-expo`); the API uses Vitest (NestJS 12's default for ESM projects). Each workspace runs its own.
- **How `@fandex/core` is consumed:** its `exports` map points the `source` / `react-native` / `browser` conditions at `src/index.ts` (Metro, the app's tsc and Vitest use these — no build needed) and `types` / `default` at `dist/` (built with tsdown, for Node). Only the API's runtime, build and typecheck need `dist`; `npm run typecheck`, and the API's `build`/`dev` scripts, build core first. `dist/` is gitignored.
- **API (NestJS 12):** ESM project (`"type": "module"`, `module: nodenext`), so relative imports in `apps/api` need `.js` extensions (`./app.module.js`). Config is validated with a zod schema (`src/config/env.ts`) via `ConfigModule.forRoot({ validationSchema })`. Shared app setup lives in `setup-app.ts` so e2e tests use the same configuration as `main.ts`. OpenAPI docs at `/docs`.
- **Local database:** `npm run db:up` / `db:down` (Docker Compose, Postgres 18; dev-only credentials in `docker-compose.yml`). Requires Docker Desktop running. Copy `apps/api/.env.example` to `apps/api/.env`.
- **Prisma 7.10 (pinned stable):** npm's `latest` tag for the `prisma` CLI pointed at an 8.0 _release candidate_ (2026-10-05); don't upgrade to 8 until it's final. Prisma 7 specifics: connection URL lives in `apps/api/prisma.config.ts` (not the schema), the client is generated into `src/generated/prisma` (gitignored; `prisma generate` runs automatically before build/dev/typecheck/test), it connects via `@prisma/adapter-pg`, and `migrate dev` no longer runs `generate`. Schema changes: edit `prisma/schema.prisma`, then `npm run db:migrate -w @fandex/api -- --name <change>` and commit the migration.
- **Auth (Better Auth 1.7 via `@thallesp/nestjs-better-auth`):** routes under `/api/auth/*` (`sign-up/email`, `sign-in/email`, `sign-out`, `get-session`…). A **global guard protects every route**; mark public ones with `@AllowAnonymous()` and read the user with `@Session() session: UserSession`. Apps must be created with `appOptions` (`bodyParser: false`) from `setup-app.ts`. Gotchas found in Task 3: (1) with `generateId: 'uuid'` Better Auth sends **no** id, so auth models need `@default(uuid(7))`; (2) Better Auth **disables its origin/CSRF check when NODE_ENV=test** — we set `advanced.disableOriginCheck: false` so tests exercise production security; (3) its rate limiter (3 failed sign-ins → 429) is off in tests only. To see the tables Better Auth expects after an upgrade: `npx auth@<version> generate` against a throwaway config, then port the fields into `schema.prisma` with our snake_case mappings.
- **Accounts in the app:** screens use `AccountService` (`useAccountService()` / `hooks/use-account.ts`), never Better Auth directly. `auth-client.ts` is the only file that imports Better Auth's runtime (jest-expo can't parse its ESM, and tests use `FakeAccountService` from `test-utils/providers.tsx`). Current user comes from Better Auth's `getSession` (200 + null when signed out, so no 401 console noise; cached in secure storage on native). The API URL comes from `EXPO_PUBLIC_API_URL`, else the Mac's address from Expo's dev server (so a phone on the same Wi-Fi reaches it), else localhost. Server trusts `fandex://` (and `exp://` in development) via the Expo plugin.
- **Catalog API** (`GET /catalog/search?q=`, `GET /catalog/isbn/:isbn`, public): results are upserted into `catalog_item` (stable ids, shared by all users); ISBN lookups are served from the DB for 30 days (stale copy returned if Open Library is down); searches are cached in memory for 1 h (per process). All Open Library calls go through `RateLimitedCatalog` (≥350 ms apart, under the 3 req/s identified limit). `CatalogError` → 502, rate-limited → 503. Params are validated with zod via NestJS 12's `@Query('q', { schema })` + global `StandardSchemaValidationPipe({ transform: true })`. Tests replace the source with `overrideProvider(BOOK_CATALOG)`.
- **Collection API** (`GET/POST/DELETE /collection`, signed in): every query is scoped by `session.user.id` (never a request field); another user's item answers **404, not 403** (doesn't reveal it exists); `POST` is idempotent (201 new / 200 existing, safe under concurrent double taps via the unique `(user_id, catalog_item_id)` constraint); items cascade-delete with the user; catalog entries can't be deleted while owned. Isolation tests were mutation-checked (removing the user filter makes them fail). CSRF: our own routes rely on Better Auth's SameSite=Lax session cookie + JSON bodies + CORS limited to trusted origins.
- **Category classification** (`classifyBookCategory` in core): Open Library merges **subjects across all editions of a work** (The Hobbit carries "Graphic novels" from its adaptations), so presence of a comic subject isn't enough. Order: edition publisher (VIZ/Kodansha… → manga; DC/Marvel/Image… → comic), then manga/comic subjects must be ≥10% of the work's subjects; "History and criticism"-type subjects are ignored. Expect occasional misfiles → a per-item override is a likely follow-up.
- **LEGO (Rebrickable):** `RebrickableCatalog` in core (`searchSets` with `min_parts=1` to drop merchandise; `lookupSet`; theme list fetched once and cached 24 h to resolve "Star Wars > Ultimate Collector Series"). API: `GET /catalog/search?q=&kind=lego`, `GET /catalog/lego/:setNumber` ("75192" → "75192-1"). Sets are stored in `catalog_item` with `set_number`, `piece_count`, `theme`, `subtheme`. Both upstreams share `RequestSpacer` (Open Library 350 ms, Rebrickable 1 s).
- **Tests are hermetic:** `ConfigModule` ignores `.env` when `NODE_ENV=test` (found in Task 9: a test silently used the developer's real Rebrickable key). The e2e env in `vitest.config.e2e.ts` provides every variable.
- **Deployment (Render free + Neon free; `render.yaml`):** one Render web service runs the API **and serves the exported web app** (`WEB_APP_DIR`, SPA fallback in `src/web-app.ts`) from the same origin, so the web session cookie is first-party. All API routes are under **`/api`** (`setGlobalPrefix`; docs at `/api/docs`, health at `/api/health`); the app's `apiFetch` adds the prefix. Build: `npm ci --include=dev && npm run build:deploy`; start: `npm run start:deploy` (runs `prisma migrate deploy` first — Render's pre-deploy command is paid). `BETTER_AUTH_SECRET` is generated by Render; `BETTER_AUTH_URL` defaults to Render's `RENDER_EXTERNAL_URL`, and the API's own origin is always trusted. `TRUSTED_ORIGINS` includes `exp://**` while the iPhone app runs in Expo Go. **Never add a payment method to the Render workspace** (without one, Render suspends rather than bills). Email (verification/password reset) is deferred: free providers need a domain we don't own. Rate limiting relies on Render's `X-Forwarded-For` (not tamper-proof; acceptable for now). Gotchas from the first deploy: a Blueprint **drops `sync: false` variables left empty** (add them later under Environment → Edit); `DATABASE_URL` must be Neon's plain **Connection string** with pooling off — a `psql '…'` or `DATABASE_URL=…` snippet fails with Prisma `P1013` ("scheme is not recognized"). Neon free: 0.5 GB per branch. The Render and Neon MCP connectors give read access to deploys, logs and the database.
- **iPhone app via EAS Update (no Mac needed to run it):** project `@sbm2310/fandex` on Expo (personal account `sbm2310`, free plan — can't incur overage charges). `npm run update:ios -w @fandex/mobile` publishes the iOS bundle to the `main` branch with `EXPO_PUBLIC_API_URL` set to the Render URL (env vars are inlined at publish time, so a changed API URL means republishing). Expo Go must be **signed in as the project owner** to open it (Expo restriction since May 2026); `runtimeVersion` policy `appVersion` (1.0.0) works in Expo Go. Publish after app changes that should reach the phone. `eas init` rewrites `app.json` from the evaluated config — check the diff (it added duplicate plugin permissions and an empty `extra.router`).
- **Universe matching** (`packages/core/src/universes`): `UNIVERSE_SEED` (5 universes, ~110 characters, Wikidata ids verified against Wikidata labels — one guessed id turned out to be a volleyball player) and `matchUniverses(signals)`. A universe matches on one strong signal (LEGO theme or parent theme, title/series/subject phrase, fictional place, distinctive character name); characters then match by exact name inside matched universes. Guards: `ambiguous` characters (Thor, Robin, Iron Man, Blade…) and names listed in two universes never establish a universe; single-word aliases ("Alfred", "Logan") don't either; authors are removed from people; `excludePhrases` veto (Star Wars ≠ Strategic Defense Initiative); only the exact "Name (Fictitious character)" subject form counts as a character (the ", fiction" variants are merged from other works — The Hobbit carries Frodo that way). Rebrickable minifig names carry outfit details after " - ", "," or " with ". Tests use `__fixtures__/signals.json` (real recorded data); the four guards were mutation-checked. Rivendell (10316) is in the Icons theme, not LOTR — themes alone aren't enough.
- **Match signals** (Stage 3 Task 2): adapters attach `matchSignals` (core `MatchSignals`, zod `matchSignalsSchema` with `exactOptional` because of `exactOptionalPropertyTypes`) and books a `workKey`; the API stores them in `catalog_item.match_signals` (jsonb) / `work_key` and never sends signals to the apps. Open Library search requests `person` and `place` (no series field exists; `q=edition_key:OL…M` finds an edition). Rebrickable: `legoThemeIds` = own theme then parents; minifigs only on `lookupSet` (absent = not fetched, `[]` = none; a failed minifig call still returns the set); a LEGO search upsert keeps stored minifigs. Rebrickable spacing is now **per HTTP request** via the adapter's `beforeRequest` hook (a lookup is 2 requests). `CatalogSignalsService`: backfills owned items needing signals in the background on start (not in tests; Render has no free one-off jobs), `refreshSoon` fetches minifigs after a LEGO set is added (LEGO only — a book refresh in tests would hit the real Open Library), writes only signal columns (`updateMany`, so a deleted row is fine), and the app waits for it on shutdown (`idle()` in tests).
- **Universes in the API** (Stage 3 Task 3): tables `universe`, `character`, `catalog_item_universe`, `catalog_item_character` (automatic links, cascade), `sync_state`. `UniverseSeedService` (in `onModuleInit`, so before requests) syncs the seed when `seedHash()` (seed + `UNIVERSE_MATCHER_VERSION`) changes: upserts by slug (ids stay stable), deletes universes/characters the seed dropped, then `UniverseLinker.relinkAll()`. **Bump `UNIVERSE_MATCHER_VERSION` in core when matching rules change.** Links are rewritten on every catalog upsert (`CatalogService.save`) and signals refresh; responses load them with `linksInclude`/`linksFromRow` (seed order). Contract: `universes: string[]`, `characters: {universe, character}[]` on catalog items, both `.default([])` so older payloads still parse. Public `GET /universes`, `GET /universes/:slug` (parsed through the zod schemas so no internal fields leak). `resetDatabase` keeps `universe`, `character`, `sync_state` (reference data); tests that change them must restore them.
- **Collection by universe** (Stage 3 Task 4): `GET /collection/universes` (signed in) returns the universes the user owns items from — `itemCount`, `categoryCounts` (only non-zero), up to 4 newest `coverUrls`, and characters with counts — computed by core's pure `summarizeCollectionUniverses(items, directory)`, which the app reuses for guest mode (the seed itself works as the directory). Crossovers count in each universe. Today the links are the automatic ones; Task 7's manual fixes will apply on top.
- **Universes in the app** (Stage 3 Task 5): catalog entries carry `universes` / `characters` (copied from API responses in `catalog-mapping.ts`, omitted when empty), so device snapshots keep them — guest items saved before Stage 3 have none until moved to an account. The Universes tab and `universe/[slug]` page compute everything on the device (`hooks/use-universes.ts`: core's `summarizeCollectionUniverses` with `UNIVERSE_SEED` as the directory), so guests and accounts share one path and it updates instantly; `GET /collection/universes` isn't used by the app (kept for later, e.g. public pages). Universe pages lay out `GridItem`s in wrapping rows (`useGridLayout` from `collection-grid.tsx`), not nested FlatLists. **Typed routes:** new route files need Expo's generated `.expo/types/router.d.ts` refreshed (start the dev server once), or `tsc` rejects the new hrefs locally (CI has no generated file).
- **Character pages** (Stage 3 Task 6): routes `universe/[slug]/index.tsx` and `universe/[slug]/[character].tsx` (URL `/universe/middle-earth/gandalf`; root Stack names `universe/[slug]/index` and `universe/[slug]/[character]`). Core has `findUniverse` / `findCharacter` (seed lookups). `UniverseChips` / `CharacterChips` (`components/universe-links.tsx`) render link chips for slugs the seed knows (real `<a href>` on web); used on universe pages, item detail and search rows (`EntryRow` puts them outside its grouped accessibility label). `CategorySections` groups items by category. Known gap: guest LEGO sets have no characters (the saved search result has no minifigs).
- **Manual fixes** (Stage 3 Task 7): an owned item stores `linkEdits` (added/removed universes and characters, as _differences_ from the automatic links — core `diffLinks`/`applyLinkEdits`) and, for books, a corrected `category` (`item.category` is what the user sees; `item.catalog.category` stays the source's). **Always read links through core's `itemLinks(item)`**, never `item.catalog.universes`. Rules: removing a universe removes its characters; a wanted character's universe counts as wanted. `CollectionRepository.update(id, changes)` (null = reset, omitted = keep); device repo applies `applyItemChanges`, the API (`PATCH /collection/:id`, columns `category_override`, `link_edits`) validates slugs against the universe tables and stores nothing when a value equals the automatic one. Fixes live on collection items, so re-matching never erases them. The edit screen (`app/edit/[id].tsx`, modal) must close with `router.canGoBack() ? back() : replace(item)` — opened by URL or after a reload there's no history (found on web).
- **Other editions** (Stage 3 Task 8): catalog responses carry `workKey` (Open Library work id); app entries keep it, so owned snapshots have it. Core `findOtherEditions(entry, items)` = owned books with the same work key but a different edition (`isSameBook` false); ownership stays per edition, so the result can still be added. `OtherEditionNote` (search rows, via `EntryRow`'s `note` slot, only when the entry itself isn't owned) and `AlsoOwnedEditions` (detail) link to the owned copy. Guest items saved before this have no work key, so no hint for them.
- **Web tab bar at phone width** (found in Stage 3 Task 9): with four tabs the top bar was wider than a 375 px screen, so the whole web page scrolled sideways (and clicks landed off target). Below 520 px it drops the "Fandex" label and tightens padding (`app-tabs.web.tsx`). Check `document.documentElement.scrollWidth === innerWidth` at phone width after adding nav items. README screenshots are 750×1624: the browser pane's mobile preset, captured at scale 1.
- **AI shelf reading** (Stage 4 Task 1): core has `shelfPrompt`, `parseShelfReply` (one line per item, `kind | title | english | author | count | set`; drops malformed, publisher-only "MARVEL" and repeated lines — models loop), `planShelfTiles` (overlapping strips along the long side) and `scoreShelfReading`. The API's `ChatClient` (`src/ai/chat-client.ts`, plain `fetch`, any OpenAI-compatible provider) turns 429 into `AiRateLimitError` (with `Retry-After`) and gives up after 30 s (requests do hang — Gemini's free tier once never answered a real scan, hence the Groq fallback below). Groq counts the prompt **plus the maximum reply length** against the token limits, so keep `maxTokens` small (800). Settings that worked: temperature 0.6, top-p 0.95, reasoning off (`reasoning_effort: low` spent 3,000 tokens thinking and answered nothing), line format (strict JSON looped too and costs double). **Evaluation:** `npm run eval:shelf -w @fandex/api` (real Groq, never in CI; `--variants`, `--photos`, `--bands`, `--prompt`) scores replies against `apps/api/eval/shelf-expected.json`; photos live in the gitignored `apps/api/eval/photos/`, runs in `eval/runs/`. A full run (~50 requests) uses a day's free token allowance. Scripts in `apps/api` run with `tsx` after building core (`preeval:shelf`); `sharp` crops the photos. `--provider gemini` (key `GEMINI_API_KEY`, comparison only) uses Gemini's OpenAI-compatible endpoint with `reasoningEffort: 'none'` (Gemini 3 thinks by default and spends the reply budget); its free tier allows **20 requests/day per model**, often answers 503 "overloaded", and `gemini-3.8-flash` didn't answer at all — measured much better reading (Hebrew, built LEGO) but unusable for production. Mistral's free plan (only Ministral models) was compared once, scored no better than Groq, and was removed from the script.
- **AI in the API** (Stage 4 Task 2): `AiModule` — `ChatClient` (`src/ai/chat-client.ts`, any OpenAI-compatible provider; `ChatModel` interface behind the `CHAT_MODEL` token, null without `GROQ_API_KEY` → AI endpoints 503, like LEGO without a key), `ShelfReader` (core's prompt, parser and `SHELF_READING_SETTINGS`), `AiQuotaService` (table `ai_usage (user_id, day DATE, kind)`, UTC days; checked before the request, **counted only after success**, so provider failures cost nothing; per-user limit → 429, everyone's daily limit → 503). `POST /api/ai/shelf-scans` is **multipart** (`images`, 1–3 JPEGs ≤ 2 MB, checked by magic bytes; `FilesInterceptor` with memory storage) because the auth module's global JSON parser keeps Express's 100 KB limit; provider 429 → our 503 with the provider's `Retry-After`, other failures → 503 with `Retry-After: 30`. `GET /api/ai/quota` → `{ available, shelfScans: { used, limit } }`. Contracts in core (`contracts/ai.ts`). Settings: `AI_BASE_URL`, `AI_VISION_MODEL`, `AI_SHELF_SCANS_PER_USER` (5), `AI_SHELF_SCANS_PER_DAY` (30; each scan reads the photo twice). e2e tests override `CHAT_MODEL` with a fake; quota isolation, the global limit and "not charged on failure" were mutation-checked.
- **Shelf readings → catalog** (Stage 4 Task 3): core `matchShelfReadings(readings, catalog, key, onError)` searches each reading (query: title + author, else + "manga"/"comics"; **retries the plain title** when that finds nothing, since Open Library wants every word to match), ranks with `scoreEntry` (title similarity ≥ 0.6 — mostly "everything read is in the title or subtitle"; +category, +author, +volume 1 for a run, LEGO: +set number read, newer sets first, 7-digit promo numbers last), keeps ≤ 4 candidates, and drops a reading whose best candidate an earlier one claimed. A LEGO set number is looked up but only counts if the set's name resembles the reading (models invent numbers: "75020" for an X-wing is Jabba's Sail Barge). The API (`ShelfScanService`) plugs in `CatalogService` (same cache and spacing as search; LEGO only with a key) and marks candidates the user owns.
