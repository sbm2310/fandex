# Fandex core — notes for Claude

Loaded when working in `packages/core` (domain types, catalog adapters, matching, parsing, contracts). Project overview, rules and roadmap: the root [CLAUDE.md](../../CLAUDE.md). Add new core gotchas here.

- **Category classification** (`classifyBookCategory` in core): Open Library merges **subjects across all editions of a work** (The Hobbit carries "Graphic novels" from its adaptations), so presence of a comic subject isn't enough. Order: edition publisher (VIZ/Kodansha… → manga; DC/Marvel/Image… → comic), then manga/comic subjects must be ≥10% of the work's subjects; "History and criticism"-type subjects are ignored. Expect occasional misfiles → a per-item override is a likely follow-up.
- **LEGO (Rebrickable):** `RebrickableCatalog` in core (`searchSets` with `min_parts=1` to drop merchandise; `lookupSet`; theme list fetched once and cached 24 h to resolve "Star Wars > Ultimate Collector Series"). API: `GET /catalog/search?q=&kind=lego`, `GET /catalog/lego/:setNumber` ("75192" → "75192-1"). Sets are stored in `catalog_item` with `set_number`, `piece_count`, `theme`, `subtheme`. Both upstreams share `RequestSpacer` (Open Library 350 ms, Rebrickable 1 s).
- **Universe matching** (`packages/core/src/universes`): `UNIVERSE_SEED` (5 universes, ~110 characters, Wikidata ids verified against Wikidata labels — one guessed id turned out to be a volleyball player) and `matchUniverses(signals)`. A universe matches on one strong signal (LEGO theme or parent theme, title/series/subject phrase, fictional place, distinctive character name); characters then match by exact name inside matched universes. Guards: `ambiguous` characters (Thor, Robin, Iron Man, Blade…) and names listed in two universes never establish a universe; single-word aliases ("Alfred", "Logan") don't either; authors are removed from people; `excludePhrases` veto (Star Wars ≠ Strategic Defense Initiative); only the exact "Name (Fictitious character)" subject form counts as a character (the ", fiction" variants are merged from other works — The Hobbit carries Frodo that way). Rebrickable minifig names carry outfit details after " - ", "," or " with ". Tests use `__fixtures__/signals.json` (real recorded data); the four guards were mutation-checked. Rivendell (10316) is in the Icons theme, not LOTR — themes alone aren't enough.
- **Match signals** (Stage 3 Task 2): adapters attach `matchSignals` (core `MatchSignals`, zod `matchSignalsSchema` with `exactOptional` because of `exactOptionalPropertyTypes`) and books a `workKey`; the API stores them in `catalog_item.match_signals` (jsonb) / `work_key` and never sends signals to the apps. Open Library search requests `person` and `place` (no series field exists; `q=edition_key:OL…M` finds an edition). Rebrickable: `legoThemeIds` = own theme then parents; minifigs only on `lookupSet` (absent = not fetched, `[]` = none; a failed minifig call still returns the set); a LEGO search upsert keeps stored minifigs. Rebrickable spacing is now **per HTTP request** via the adapter's `beforeRequest` hook (a lookup is 2 requests). `CatalogSignalsService`: backfills owned items needing signals in the background on start (not in tests; Render has no free one-off jobs), `refreshSoon` fetches minifigs after a LEGO set is added (LEGO only — a book refresh in tests would hit the real Open Library), writes only signal columns (`updateMany`, so a deleted row is fine), and the app waits for it on shutdown (`idle()` in tests).
- **Manual fixes** (Stage 3 Task 7): an owned item stores `linkEdits` (added/removed universes and characters, as _differences_ from the automatic links — core `diffLinks`/`applyLinkEdits`) and, for books, a corrected `category` (`item.category` is what the user sees; `item.catalog.category` stays the source's). **Always read links through core's `itemLinks(item)`**, never `item.catalog.universes`. Rules: removing a universe removes its characters; a wanted character's universe counts as wanted. `CollectionRepository.update(id, changes)` (null = reset, omitted = keep); device repo applies `applyItemChanges`, the API (`PATCH /collection/:id`, columns `category_override`, `link_edits`) validates slugs against the universe tables and stores nothing when a value equals the automatic one. Fixes live on collection items, so re-matching never erases them. The edit screen (`app/edit/[id].tsx`, modal) must close with `router.canGoBack() ? back() : replace(item)` — opened by URL or after a reload there's no history (found on web).
- **AI shelf reading** (Stage 4 Task 1): core has `shelfPrompt`, `parseShelfReply` (one line per item, `kind | title | english | author | count | set`; drops malformed, publisher-only "MARVEL" and repeated lines — models loop), `planShelfTiles` (overlapping strips along the long side) and `scoreShelfReading`. The API's `ChatClient` (`src/ai/chat-client.ts`, plain `fetch`, any OpenAI-compatible provider) turns 429 into `AiRateLimitError` (with `Retry-After`) and gives up after 30 s (requests do hang — Gemini's free tier once never answered a real scan, hence the Groq fallback below). Groq counts the prompt **plus the maximum reply length** against the token limits, so keep `maxTokens` small (800). Settings that worked: temperature 0.6, top-p 0.95, reasoning off (`reasoning_effort: low` spent 3,000 tokens thinking and answered nothing), line format (strict JSON looped too and costs double). **Evaluation:** `npm run eval:shelf -w @fandex/api` (real Groq, never in CI; `--variants`, `--photos`, `--bands`, `--prompt`) scores replies against `apps/api/eval/shelf-expected.json`; photos live in the gitignored `apps/api/eval/photos/`, runs in `eval/runs/`. A full run (~50 requests) uses a day's free token allowance. Scripts in `apps/api` run with `tsx` after building core (`preeval:shelf`); `sharp` crops the photos. `--provider gemini` (key `GEMINI_API_KEY`, comparison only) uses Gemini's OpenAI-compatible endpoint with `reasoningEffort: 'none'` (Gemini 3 thinks by default and spends the reply budget); its free tier allows **20 requests/day per model**, often answers 503 "overloaded", and `gemini-3.8-flash` didn't answer at all — measured much better reading (Hebrew, built LEGO) but unusable for production. Mistral's free plan (only Ministral models) was compared once, scored no better than Groq, and was removed from the script.
- **Shelf readings → catalog** (Stage 4 Task 3): core `matchShelfReadings(readings, catalog, key, onError)` searches each reading (query: title + author, else + "manga"/"comics"; **retries the plain title** when that finds nothing, since Open Library wants every word to match), ranks with `scoreEntry` (title similarity ≥ 0.6 — mostly "everything read is in the title or subtitle"; +category, +author, +volume 1 for a run, LEGO: +set number read, newer sets first, 7-digit promo numbers last), keeps ≤ 4 candidates, and drops a reading whose best candidate an earlier one claimed. A LEGO set number is looked up but only counts if the set's name resembles the reading (models invent numbers: "75020" for an X-wing is Jabba's Sail Barge). The API (`ShelfScanService`) plugs in `CatalogService` (same cache and spacing as search; LEGO only with a key) and marks candidates the user owns. Response: `{ items: [{ reading, candidates: [{ item, owned }] }], quota }`. Readings are often in capitals and misspelled ("UNLAND SAGA" finds nothing — that reading comes back without candidates). A real scan of one shelf takes ~8 s (model ~3 s, then ~20 searches 350 ms apart). **Concurrency bug found here:** simultaneous saves of the same catalog item collided on the universe link tables (P2002); link inserts now use `skipDuplicates`. **The Groq key's daily 200K tokens are shared by everything using that Groq account** — local testing and `eval:shelf` runs eat into the production allowance.
- **Reading each photo twice** (after the first iPhone scans offered invented titles such as "Black Clover"): the model's inventions change between readings while real titles come back, so `ShelfReader` sends two identical requests at once and core's `combineShelfReadings` pairs them (`readingAgreement`: shared words over all words ≥ 0.6, or a title of 2+ words read whole inside the other — "Civil War" / "X-Men: Civil War"; a shared series name alone, "Spider-Man: Gold" / "Spider-Man: Red", isn't enough). Items carry `sure` (contract default `true`); sure ones come first and start ticked, the rest are listed under "Less sure", unticked. If one of the two requests fails, the other's readings are used, all marked sure. Measured on two saved Groq runs (`npx tsx eval/agreement.ts <run> <run>`, no model calls): 20 of 29 sure readings were real (69%, vs 41% for one reading), and the two readings together found 26 of 52 items vs 22. (First reported as 90% — that pair was accidentally a Groq run and a Mistral run; **check a run's model in its `summary.md` header before comparing runs**.) Cost: twice the tokens (so ~30 scans a day for everyone), and two simultaneous requests come close to Groq's 8K tokens a minute.
- **Ask: the query engine** (Stage 4 Task 6, `packages/core/src/ask/`): `collectionQuerySchema` (universes, characters, categories, title words, creator, `addedAfter`/`addedBefore` as UTC `YYYY-MM-DD` with the end exclusive, sort, `answer: list | count`, `unsupported` with a reason). Within a filter any value matches; across filters all must. `runCollectionQuery` reads links through `itemLinks` and the user-facing `item.category`, so manual fixes count (mutation-checked). `describeAnswer` → "You own 3 Batman items: 2 comics and 1 LEGO set." (breakdown only when categories mix). `parseQuestionLocally(question, { seed, today })` is the no-AI fallback: unsupported topics first (missing volumes, pre-orders/releases, prices), then universe names/aliases (+ a few question-only ones: Tolkien, LOTR), **longest phrase first and blanked once matched** (so "Harry Potter books" is the universe, not the character; "graphic novels" are comics, not novels), then character names (skipping ones two universes share and everyday words like "child"/"merry"), categories, "how many", and date phrases (today, this week/month/year, last month/year, recently = 30 days).
- **Figures and custom items** (Stage 5 Task 1): category `figure` (in `CATEGORIES`, so filters, badges, universe pages and Ask know it) and core's `CatalogFigure` (`source: 'custom'`, `brand`, `line`, `scale`, `coverUrl`; `catalog-figure.ts`: `createFigure` matches universes from the name with the line as a series, `trimmed`, `figureDetails`). `CatalogEntry` = book | set | figure — **narrow with `isBookEntry` / `isBookItem`, not `category !== 'lego'`** (that used to mean "a book"). API: `POST /api/catalog/custom` (signed in; `CustomItemsController`, since `CatalogController` is public) stores it in `catalog_item` with `source = custom`, `owner_id` (cascade with the user), brand → `creators`, line → `subtitle`, new `scale` column; `CollectionService.add` answers 404 for someone else's custom item (mutation-checked), `remove` deletes the user's own custom item with the copy, and a figure's category can't be changed. The `collection_item → catalog_item` FK is `NO ACTION` (checked at statement end) so deleting an account removes its figures and copies together. App: the Add tab's switch is **Books | LEGO | Figures**; Figures shows `AddFigureForm` (`components/add-figure-form.tsx`) in place of the search, since there's no figure catalog to search (`useAddFigure`: signed in → `CustomItems.createFigure` on the API; guest → core's `createFigure` with an `expo-crypto` UUID, saved on the device; after saving it pushes the figure's page and clears itself); moving a guest collection into an account saves device figures through `customItems` too. Figures render like LEGO (square, `contain`), with brand · scale and the line as details. The move banner now says "items", not "books".
- **Pre-orders in core** (Stage 5 Task 2, `packages/core/src/preorders/`): **money** is integer minor units + `Currency` (`CURRENCIES`: USD, EUR, GBP, CAD, AUD, JPY, ILS); `formatMoney`/`currencyDigits` go through `Intl` (JPY has 0 decimals), `parseMoney` splits the string (never float math; more decimals than the currency → null), `moneyInputValue` for form fields. **Release dates** are `{ date, precision: day | month | quarter | year }` with `date` normalized to the period's first day (`releaseDate`); `releasePeriodEnd` is what comparisons use ("March 2027" isn't late until April), `formatRelease` → "Q1 2027", `compareReleases`, `daysBetween`/`addDays` on `YYYY-MM-DD`. **Rules** (pure, "today" passed in): `balanceLeft`, `needsAttention` (payment overdue / due within `ATTENTION_DAYS` = 7, release period passed, arriving on a day within 7; open pre-orders only), `groupUpcoming` (attention by urgency, this month = period ends by month end, later, no date, `owed` per currency), `summarizeSlips`/`describeSlips` (only moves to a later date count; "Delayed twice, originally March 2027"). **Contracts** (`contracts/preorders.ts`): `preorderSchema` (with `catalog` and `history`), create (paid ≤ price, `orderUrl` http(s) only, text trimmed, dates normalized) and update (null clears; status only ordered ↔ cancelled — arriving has its own endpoint). Three rules mutation-checked.
- **Ask about pre-orders** (Stage 5 Task 7): `CollectionQuery` has `scope: collection | preorders` and pre-order filters `arrivingAfter`/`arrivingBefore` (exclusive; judged by the **end** of the expected period, like the Upcoming tab), `balanceDue`, `delayed` (a later move in the history); the shared filters apply to the pre-ordered item and `added*` means ordered. Core's `runPreorderQuery(preorders, query, view)` looks at **open** pre-orders only, sorts soonest first (no date last), and returns `owed` per currency; `queryablePreorder(response)` is the view both the API (`PreordersService.queryable`, no Open Library check) and the app use. `describeAnswer` writes "You have 1 pre-order arriving in October 2026. Still owed: $280.00." / "You still owe $1,129.99 and €250.00 on 3 pre-orders." The model reply has every new field (`resolveModelQuery` drops pre-order filters from a collection query); the keyword fallback detects pre-order words (arriving, coming out, owe, balance, delayed…) and reads arrival periods (this/next week, month, year, soon). Item value/spending is still unsupported. `AskResponse.itemIds` are pre-order ids for that scope; the app looks them up in `usePreorders()` and shows `PreorderRow`s; guests asking about pre-orders get `PREORDERS_NEED_ACCOUNT`. `useAsk().ready` waits for pre-orders when signed in (or their error). Replies re-recorded for 18 questions (5 about pre-orders) with Groq.
- **Volumes from titles** (Stage 6 Task 1, `packages/core/src/series/volumes.ts`): `parseVolume` reads manga/comic titles — "Vol. 24", "Volume 7", "#5", a subtitle "Volume 6 (…)", and a bare trailing number for **manga only** ("ONE PIECE 113"; comics have "Spider-Man 2099") — rejecting bundles ("Vol. 19-24", box sets), 0 and 4-digit numbers. Series key: `normalizeName` (no leading "the"), "×" → "x", other scripts kept as typed. `volumeGaps` groups by category + key, lists `missing` from 1 to the highest owned; `formatVolumeRanges` → "1–3, 5 and 7–112". On the local catalog, 110 of 494 manga/comics parsed as volumes, all plausible; edition lines (VIZBIG) stay separate series.
- **Wikidata series** (Stage 6 Task 2, `catalogs/wikidata-series.ts`): `WikidataSeriesCatalog.seriesForWork(workKey)` sends one SPARQL query (`seriesQuery`; the work key is validated as `OL\d+W` because it goes into the query) and `parseSeriesResponse` turns rows into `BookSeries` — `entries` = whole-number places ≥ 1, one per place (preferring one with an Open Library work id), `extras` = novellas, fractional/0.5 places, unnumbered and duplicate items. Several series (Mistborn + Cosmere): the one the book is numbered in, then the most numbered books. Labels need `wikibase:language "en,mul"` (Harry Potter's series has only a multilingual label). Members filtered to literary works (`P31/P279* Q7725634`). Fixtures: 5 real responses (Stormlight, Harry Potter, Mistborn, ACOTAR, The Hobbit = none). Core `seriesProgress(series, ownedWorkKeys)` and `isUpcoming(entry, today)`; contract `workSeriesResponseSchema`. CatalogError sources include `wikidata`.
- **Next volume** (Stage 6 Task 4, `series/next-volume.ts`): no endpoint — `findNextVolume(series, search)` uses the normal book search with `nextVolumeQuery` ("<series key> <n+1>", e.g. "hunter x hunter 38": the key drops "&"/"×" that would break Open Library's every-word matching) and `pickVolume` keeps only results that parse (as the **series'** category) to the same key and number. Fixtures: 5 real searches (`openlibrary-search-next-*`). **Running ad-hoc scripts:** put them in `apps/api/eval/` (resolves `@fandex/core`, not watched); a file added under `apps/api/src/` restarts the dev API.
- **Ask about series** (Stage 6 Task 7): query scope `series` (`QUERY_SCOPES`). Core `summarizeSeries(items, seriesForWork)` → `SeriesStatus` (name, category book/manga/comic, owned, total, missing) — book series by work id, volumes by `volumeGaps` — used by the API (`CollectionService.seriesItems` + `SeriesService.forWorks`, in `QuestionAnswerer.answer`) and the app (`utils/ask.ts` `seriesItems`; `useAsk` fetches owned books' series for keyword answers, none offline). `runSeriesQuery` keeps series with something missing, filtered by category and title words in the series' name; `describeAnswer` → "You're missing books 3–5 of The Stormlight Archive." / "…from 2 series: One Piece (volume 2) and …" (≤ 5 listed) / "You aren't missing anything from your manga series." / count. Series answers have no `itemIds`; the Ask screen links to "Your series ›". Keyword fallback: "missing", "gaps", "incomplete", "complete the series", "next volume" (pre-order words win); title words = what's left after `SERIES_FILLER`. Replies re-recorded (20 questions). **Live-test gotcha:** pick catalog items by exact title — "one piece 3" also finds "One Piece 3-In-1 Edition … Set" (a bundle, rightly not a volume). Some volumes are filed as **book** by the category classifier (e.g. a "One Piece, Vol. 1: Romance Dawn" edition) and then aren't read as volumes until the user fixes the category.
- **Figures in core** (Stage 7 Task 1, `packages/core/src/figures/`): `FIGURE_BRANDS` (brands, aliases, lines with box codes: Hot Toys MMS/DX/TMS/VGM/CMS/QS/PPS/ACS/COSB; InArt without numbers so far), `parseFigureNumber` (whole string, canonical text without leading zeros: "TMS007" → "TMS 7"; die-cast "D30" kept separately) and `findFigureNumber` (inside text). `CatalogFigure.source` is `fandex` (shared, curated) or `custom` (private); new fields `number`, `edition`, `release`, `price` (`Money` = minor units + currency). Contract fields are named `figureNumber` / `releaseDate` (books already use `publishDate`). `sameFigure` is for spotting duplicate suggestions: numbers decide when both have one. `NewFigure` / the add-by-hand request don't take the new fields yet (Task 3 adds the columns).
- **The curated figure list** (Stage 7 Task 2): JSON in `packages/core/src/figures/seed/` (`inart.json`, `hot-toys-{star-wars,marvel,dc}.json`), loaded and parsed by `figures/figure-seed.ts`, exported **only** as `@fandex/core/figure-seed` (a second `exports` entry and tsdown entry) so Metro never bundles it; schema/validator/`figureFromSeed` are in the main index. `figure-seed.test.ts` runs `figureSeedProblems` over the real list — adding an entry with an unknown character, a duplicate number or a badly written number fails CI. Entry ids are permanent (`hot-toys-mms-279`, `inart-gandalf-the-grey`; editions and scales as suffixes) — they become catalog external ids. Prices are `"USD 445.00"` (InArt: first pre-order full payment; Hot Toys: Action Figure 411's US retail); anything sources disagree on goes in `note`. Hot Toys numbers come from Action Figure 411's checklists (codes there: M = MMS, T = TMS, D = DX, C = CMS, V = VGM, "B" = Special Edition, "AE" = Artisan Edition) and are each confirmed by a second page. Characters must exist in the universe seed (extend the seed to link more).
- **Reading figure boxes** (Stage 7 Task 7, `packages/core/src/ai/box-*.ts`, `score-box.ts`): one box → labelled lines, parsed by `parseBoxReply`; `matchBoxReading` takes the box number first (exact `sameFigureNumber`), else searches the name then the character with core's `searchFigures`. Evaluation: `npm run eval:boxes -w @fandex/api` (photos in the gitignored `apps/api/eval/box-photos/`, facts in `eval/boxes-expected.json`: `file`, optional `sides` (other photos of the same box), `brand`, `number` as printed, `name`, `aliases`, `figureId` of the curated entry). Gemini's free tier shares its 20 requests a day with production shelf scans.
